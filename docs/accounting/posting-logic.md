We post transacctions in three steps:

**Core rules**

- Ledger is in reporting currency.
- At the time of posting, we use the locked rate (either as generated by the system or custom rate added by user)
- Only monetary items can create FX exposure. Exposures are revalued exposures month-end and realized on settlement.
- Non-monetary items measured at historical cost never get FX revalued. Ever.

**Accounting basis effect**
Mod cash basis

- Since we do not create AR/AP from revenue/expense. No exposure from those flows
- We still revalue any foreign-currency cash and loans monthly
- Bank → P&L posting:
  ```js
  - Translate at bank-date rate.
  - is_monetary=false for the P&L line.
  - If the bank account is foreign currency, it is monetary. Track it on the fx_position table
  ```

Modified accrual (default for businesses)

- We create AR/AP and similar when control transfers or obligations arise
- Those AR/AP/loans are monetary exposure and we revalue monthly until settlement
- Settlement posts realized FX gains or losses

**Posting Decision Tree**

- Determine if this transaction is monetary or not. (coa's account type, transaction currency !== reporting currency)
- Not monetary, post straight. Monetary? Determine FX impact and post accordingly. Create fx_position entry

How it works
A. Bank to P&L - Basis: cash or accrual → same result here. - Expense Leg: Post P&L at custom_exchange rate (same as system ex rate if user doesn't add new custom ex rate) - Bank Leg: Bank if foreign currency: make entry in ledger/coa, update/create fx position
B. Accrual journal that hits a monetary account (e.g. AP for an expense) - Non-monetary line, no fx_position entry - Monetary line - update fx_position

    C. Settlement of a monetary exposure via the bank
        - Identify the fx_position entry from the original entry
        - compute realized FX against the lot's current carrying value
        - Post:
            - Reduce AR/AP/Loan by its carrying slice.
            - Credit/Debit cash by translated cash amount.
            - Offset to Realized FX for the difference.

    D. Non-monetary at historical cost (inventory, PPE, prepayments)
        - Translate once at recognition. is_monetary=false. No revaluation
        - Depreciation/amortization uses the base-currency carrying values. No FX.

    E. Loans (monetary)
        - Every principal movement creates or adjusts a loan lot.
        - Revalue monthly until settled or converted.

- Disallow soft-deleting revaluation and settlement JEs.

**Examples**

- Accrual AP then settlement (modified accrual, USD reporting, EUR exposure)
  - 2025-09-01 journal: Expense EUR 10,000 @1.10; Credit Accounts Payable 11,000.
  - is_monetary=true on AP;
  - Position: open_fx_amount=10,000, carrying_base_amount=11,000.
  - 2025-09-30: Rate is now 1.12
  - reval @1.12: new_base 11,200 → post Unrealized loss 200; AP +200.
  - Position: carrying_base_amount=11,200.
  - 2025-10-05 pay EUR 10,000 @1.15: cash_base 11,500.
  - Carry_slice = 11,200. Realized loss = 300.
  - Post: DR AP 11,200; DR Realized FX 300; CR Cash 11,500.
  - Position closes.

- Cash-basis subscription from EUR bank (USD reporting)
  - 2025-09-10 bank fee EUR 50 @1.15: Expense 57.50; Cash-EUR −50.
  - Expense line non-monetary. updates: open_fx_amount += 50, carrying_base_amount += 57.50.
  - 2025-09-30 reval @1.12: new_base 56.00 → Unrealized loss 1.50; Cash −1.50.
  - Position remains open until you convert or spend the rest.

FX Transaction ID (fx_transaction_id)
fx_transaction_id identifies a foreign-currency exposure lot.
All monetary lines related to the same exposure (initial recognition, revaluations, partial settlements, reversals) carry the same fx_transaction_id.
This allows the system to:

- Track open/closed foreign-currency positions in fx_positions.
- Post realized/unrealized FX consistently.
- Close or adjust exposures when they are settled.

What it is not

- Not a pointer to a single ledger_entry or journal_entry.
- Not tied to one posting line, because exposures span multiple postings over time.

Conventions
We assign fx_transaction_id based on the object that originated the exposure:

Accrual via manual journal batch
fx_transaction_id = "JRN:<journal_batch_id>"
Example: an AP line from journal batch 42 → JRN:42.

Accrual via ledger transaction
fx_transaction_id = "LEDGER_TX:<ledger_transaction_id>".

Cash balances
fx_transaction_id = "CASH:<bank_account_id>:<currency_id>".
One per bank account and currency. Cash revals/settlements always point here.

Loans
fx_transaction_id = "LOAN:<loan_id>" (or LOAN_DRAW:<draw_id> if you support multiple draws).

Other docs (future)
When invoices/bills modules exist, use their document IDs in the same way: the doc that created the exposure.

Rules
If is_monetary = true then fx_transaction_id must be set. We can even add a db check
All lines for the same lot (origin, reval, settlement, reversal) must reuse the same fx_transaction_id.
Reversals always carry the same fx_transaction_id as the original.
Cash lines never reuse AP/AR lot IDs — they always use the cash key.

Edge cases: If a single journal_batch intentionally creates multiple independent exposures, generate one lot per exposure: e.g., two AP lines to two vendors: JRN:<batch_id>:AP1, JRN:<batch_id>:AP2 or generate two batch IDs. Keep lots disjoint.

```js
    Penning down my thoughts:
    // 1) Allowed lot types. Keep it short and stable.
    export type FxLotType = "JRN" | "LEDGER_TX" | "BANK" | "LOAN" | "LOAN_DRAW";

    // 2) Factory to build an fx_transaction_id from structured inputs.
    export function makeFxTransactionId(input:
    | { type: "JRN"; journalBatchId: string }
    | { type: "LEDGER_TX"; ledgerTransactionId: string }
    | { type: "BANK"; bankAccountId: string; currencyId: string }   // bank accounts are your “cash”
    | { type: "LOAN"; loanId: string }
    | { type: "LOAN_DRAW"; loanDrawId: string }
    ): string {
    switch (input.type) {
        case "JRN":
        return `JRN:${sanitize(input.journalBatchId)}`;
        case "LEDGER_TX":
        return `LEDGER_TX:${sanitize(input.ledgerTransactionId)}`;
        case "BANK":
        // one lot per bank account per currency
        return `BANK:${sanitize(input.bankAccountId)}:${sanitize(input.currencyId)}`;
        case "LOAN":
        return `LOAN:${sanitize(input.loanId)}`;
        case "LOAN_DRAW":
        return `LOAN_DRAW:${sanitize(input.loanDrawId)}`;
    }
    }
```
