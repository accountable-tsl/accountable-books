# Command, Bulk, Concurrency, and Realtime Contracts

## Decision

Users never complete, cancel, reopen, or mutate Work Items. Every UI action invokes a domain command against the accounting, banking, Finding, Confirmation, Engagement, or Close target. The command reloads current authority and source truth, performs the domain transition and synchronous Work reconciliation in one database transaction, commits, and only then returns the authoritative outcome and an optional queue projection delta.

Single-target commands use expected domain versions/hashes and one required `commandId`. Independent bulk bookkeeping uses an explicit bounded target manifest and one transaction per target, returning partial results. Package submission/approval and cascading reopen remain bounded aggregate commands in one all-or-nothing transaction. The SPA may show an in-flight state, but it never removes accounting work before commit confirmation.

Launch uses server-confirmed deltas for local commands and one authorized firm-scoped SSE stream for changes committed by clients, teammates, bank processing, or automation. SSE carries invalidation notices only; the SPA performs targeted refetches of authoritative DTOs. Normal connected operation does not poll. Focus/reconnect refetch and visible-tab polling while SSE is unavailable provide recovery rather than primary synchronization.

## 1. Command vocabulary and boundaries

### Domain Command

A **Domain Command** expresses the business result the actor wants against a durable domain target, such as categorize a transaction, accept a candidate, post a journal, resolve a Finding, answer a Close Confirmation, submit a Period Close, or approve a submitted Version.

It is not:

- `completeWorkItem`;
- `changeTaskStatus`;
- an arbitrary registry command supplied by the browser;
- a generic workflow transition;
- an optimistic projection edit.

The Work Type registry may advertise a bounded `commandCode` for presentation and bulk eligibility. The route/controller maps that known code to a concrete domain command; callers cannot invent a code or ask a generic executor to run it.

### Command identity and request identity

- `commandId` identifies one logical command and correlates every transport retry and resulting domain, Work, audit, activity, outbox, log, trace, and response effect.
- `requestId` identifies one HTTP attempt and is generated by the existing request-context middleware, so retries of one command have distinct request IDs.

The SPA creates one UUID for a logical command and reuses it only when retrying that unchanged command. It creates a new `commandId` when the target set or business intent changes. The API exposes no separate caller-supplied correlation ID. Existing infrastructure that physically stores a `correlation_id` records the `commandId` there; this is a storage adapter, not a second public concept.

`commandId` is neither a Work Item/domain target ID nor proof that a request is new, authorized, or semantically identical to an earlier request.

### Expected state

Expected state proves what the actor saw. It is command-specific: a row version, submitted content hash, Finding facts hash, Confirmation context hash, effective response identity, or explicit collection of target expectations. The server always reloads authoritative state and recomputes predicates after taking locks; an expected value is a concurrency guard, never source truth.

## 2. Firm-scoped command routes

Queue-initiated firm work remains under the stable firm context:

```text
/api/v2/firms/{firmCompanyId}/engagements/{engagementId}/...
```

The Engagement resolves the client company and service domain. The server verifies that the authenticated actor may use that Engagement under the firm and that every target belongs to the derived client. Changing either path ID cannot expand access.

Client-only actions, such as starting bank reauthorization, remain under the authenticated client-company context because the client contact—not a firm worker—must perform them. Their completed banking transition still reconciles the same Work Queue and Close V2 Work occurrence.

There is deliberately no route resembling:

```text
POST /work-items/{workItemId}/complete
PATCH /work-items/{workItemId}/status
DELETE /work-items/{workItemId}
```

## 3. Common request contract

Every interactive command requires JSON containing its logical command identity:

```http
Content-Type: application/json
```

Common body shape:

```ts
type CommandBody<TInput, TExpected> = {
  commandId: string; // UUID; UUIDv7 recommended
  input: TInput;
  expected: TExpected;
  presentationContext?: QueuePresentationContextDto;
};

type QueuePresentationContextDto = {
  scope: "my_work" | "portfolio" | "firm_oversight";
  clientCompanyId: string | null;
  assigneeUserId: string | null;
  sectionLimit: number;
};
```

`commandId` must be a valid UUID. `presentationContext` is optional and affects only the post-commit projection delta. The server canonicalizes and reauthorizes it exactly like the queue read endpoint. It cannot influence command authorization, target scope, or accounting state. A command sent from a workspace without a live queue context omits it and receives invalidation hints instead of an exact queue delta. The server stores no generic normalized-request hash.

## 4. Success response envelope

```ts
type CommandSuccessDto<TResult> = {
  success: true;
  data: {
    command: {
      commandId: string;
      requestId: string;
      outcome: "applied" | "already_applied" | "accepted";
      committedAt: string | null;
    };
    result: TResult;
    workEffects: WorkEffectDto[];
    presentation: {
      status: "included" | "refetch_required" | "not_requested";
      queueDelta: QueueDeltaDto | null;
      invalidations: QueryInvalidationDto[];
    };
  };
};

type WorkEffectDto = {
  workItemId: string;
  engagementId: string;
  fiscalPeriodId: string;
  workTypeCode: string;
  groupKey: string;
  transition: "opened" | "updated" | "resolved" | "superseded";
  previousVersion: number | null;
  currentVersion: number | null;
  endReasonCode: string | null;
};
```

`workEffects` explains what the committed domain command caused and supports a workspace's handled-this-session drawer. It does not tell the SPA how to classify queue rows; presentation changes come from `queueDelta` or refetch.

`committedAt` is present for `applied` and `already_applied`. `accepted` is reserved for an asynchronous operation that has not yet produced the requested authoritative outcome—for example, creating a provider reauthorization session or requesting an expensive recomputation. Accepted work remains visible until a later committed source transition actually clears it.

Post-commit projection failure must not convert a committed accounting command into an HTTP 500. The wrapper returns the successful domain result with `presentation.status = 'refetch_required'` and precise invalidation hints. A retry with the same `commandId` reloads the canonical domain outcome and may rebuild the projection without reapplying the mutation.

## 5. Error envelope and status codes

The current flat Accountable Books `ApiResponse` cannot express actionable concurrency recovery cleanly. Work Queue and Close V2 command routes use this discriminated error:

```ts
type CommandErrorDto = {
  success: false;
  error: {
    code:
      | "INVALID_INPUT"
      | "UNAUTHENTICATED"
      | "FORBIDDEN"
      | "NOT_FOUND"
      | "STALE_STATE"
      | "COMMAND_BUSY"
      | "DOMAIN_PRECONDITION_FAILED"
      | "BULK_LIMIT_EXCEEDED"
      | "SERVICE_UNAVAILABLE"
      | "INTERNAL_ERROR";
    message: string;
    retryable: boolean;
    fieldErrors?: Record<string, string[]>;
    conflict?: ConflictDto;
    retryAfterMs?: number;
    invalidations?: QueryInvalidationDto[];
  };
  meta: {
    requestId: string;
    commandId: string | null;
  };
};

type ConflictDto = {
  resourceType: string;
  resourceId: string;
  reason:
    | "version_changed"
    | "facts_changed"
    | "context_changed"
    | "target_resolved"
    | "target_replaced"
    | "approval_stale"
    | "sequence_advanced";
  expected: Record<string, unknown>;
  current: Record<string, unknown>;
  recovery:
    | "refresh_item"
    | "refresh_workspace"
    | "refresh_close"
    | "return_to_queue";
};
```

| HTTP  | Code                                   | Meaning                                                                                                                                    |
| ----- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `400` | `INVALID_INPUT`, `BULK_LIMIT_EXCEEDED` | Request shape/limit is invalid before execution.                                                                                           |
| `401` | `UNAUTHENTICATED`                      | No valid session.                                                                                                                          |
| `403` | `FORBIDDEN`                            | Authenticated actor lacks current authority.                                                                                               |
| `404` | `NOT_FOUND`                            | Missing or inaccessible firm, Engagement, target, Work Group, or Version.                                                                  |
| `409` | `STALE_STATE`, `COMMAND_BUSY`          | Concurrent state changed or a correctness lock timed out.                                                                                  |
| `422` | `DOMAIN_PRECONDITION_FAILED`           | Current authoritative state is understood but business invariants reject the request, such as close blockers or an earlier unclosed month. |
| `503` | `SERVICE_UNAVAILABLE`                  | Retryable infrastructure failure before any commit.                                                                                        |

An HTTP timeout or lost response has an unknown outcome. The client retries the unchanged logical command with the same `commandId`; it never creates a new ID merely because it did not see the response.

## 6. Retry convergence without a command-receipt table

The launch scope adds no generic command receipt, workflow run, request-hash store, or response cache. `commandId` is a retry/correlation identity, not a stored-response idempotency protocol. The API neither promises byte-for-byte response replay nor detects reuse of one ID with different input.

Every command handler must be convergent under its aggregate lock:

1. If the requested post-state already exists, return `already_applied` with the current authoritative identity/state and rebuild current projection effects.
2. If the target already reached the same valid post-state independently, return either `already_applied` with the authoritative identity or a documented no-op result.
3. If the aggregate advanced incompatibly, return `STALE_STATE`; never apply the old intent to the new state.

Correctness comes from:

- transaction-scoped advisory locks and row locks;
- expected versions/hashes/context identities;
- target-domain uniqueness, state constraints, and source links;
- deterministic/natural identities for created outcomes;
- explicit target lists for bulk requests;
- idempotent Work reconciliation and outbox scope keys.

The server carries `commandId` as correlation metadata through audit, activity, outbox payloads, logs, traces, and results. Existing `audit_events.correlation_id` and equivalent infrastructure fields store that value. Audit/outbox history is never queried on the command path to decide whether the command ran, and outbox deduplication uses stable domain-event/source identities rather than `commandId` alone.

`commandId` must not be repurposed as the identity of a newly created accounting/close row merely to obtain deduplication. Creation commands use a domain-owned natural, deterministic, or explicitly supplied result identity plus the domain's uniqueness/state constraints. Multi-row commands use deterministic child identities or verify existing rows from aggregate state.

Any external operation that cannot converge safely must solve idempotency inside that integration—for example with a provider idempotency token, a durable provider-session identity, or a contract proving duplicate creation is harmless. It does not justify a generic command-receipt table. If exact cached-response replay is ever required for third-party callers, that would be a separate API product decision.

## 7. Optimistic concurrency requirements by command family

### Accounting target commands

The request includes:

- domain target ID and its current domain version or mutation token;
- `workItemId` and `workItemVersion` when the action originated from Work, for target context and stale explanation;
- candidate ID/version or transaction posting/link version where applicable;
- every accounting selection the actor explicitly made.

Work version alone is never sufficient. Work is not the accounting source of truth.

### Accounting Finding resolution

```ts
type ResolveFindingExpected = {
  findingVersion: number;
  definitionVersion: string;
  factsHash: string;
  workItemVersion: number;
};
```

The command recomputes definition and facts under lock. `accepted` and `not_applicable` require the exact permitted strategy and nonblank reason; correction is completed only when the accounting mutation and evaluator result agree.

### Close Confirmation response

```ts
type RespondConfirmationExpected = {
  confirmationVersion: number;
  definitionVersion: string;
  contextHash: string;
  effectiveResponseId: string | null;
  workItemVersion: number;
};
```

Including the effective response identity prevents an old browser from appending over a newer answer even when the Confirmation's system context itself did not change.

### Period Close submission

```ts
type SubmitPeriodCloseExpected = {
  periodCloseVersion: number;
  draftPeriodCloseVersionId: string;
  priorClosedPeriodCloseId: string | null;
};
```

The server does not trust browser readiness counts. It locks the close sequence, fully re-evaluates Work, Findings, Confirmations, package membership, and prior-period state, then builds the submission hash/snapshot.

### Period Close approval or rejection

```ts
type DecidePeriodCloseExpected = {
  periodCloseVersion: number;
  periodCloseVersionId: string;
  contentHash: string;
};
```

Approval/rejection targets the frozen Version identity, not “the client's current close.” A material change returns `approval_stale` and points to the current draft/workspace.

### Close Package commands

Package creation requires an explicit Client Lead-confirmed `dueAt` and assignee; there is no fixed Catch-up/Reclose duration or required system-generated default. The current Client Lead inherently manages Packages for their own Engagement. `manage_close_packages` is a delegated exception for another otherwise authorized firm member and does not grant approval authority. Package reassignment/split uses `packageVersion`. Every split/replacement supplies an explicit `dueAt` for each replacement range. `changeClosePackageDeadline` requires `packageVersion`, a new `dueAt`, and a nonblank reason. Reassignment alone never changes the deadline.

```ts
type ChangeClosePackageDeadlineInput = {
  dueAt: string; // ISO-8601 timestamp normalized under the settled business-day/timezone policy
  reason: string;
};

type ChangeClosePackageDeadlineExpected = {
  packageVersion: number;
};
```

Creation, replacement, or deadline change locks the Package range and atomically persists Package `due_at` onto every covered open Period Close and Work Item. Later Work materialized inside an active Package inherits that deadline. The command response returns affected close/group invalidations or a delta only after commit.

Submission includes the current Package version and expected included draft Version IDs. Approval includes Package version plus every submitted Version ID/content hash. The all-or-nothing command revalidates the full ordered range after locking it; browser-supplied progress counts are ignored.

### Engagement responsibility commands

Replacement uses Engagement version, exact current assignment interval IDs, replacement membership ID, effective instant, and explicit rerouting/reassignment choices. It cannot silently strand Work or Packages because another browser loaded an older team roster.

## 8. Transaction protocol

The public wrapper owns the transaction. Inner services accept the existing Knex transaction and never open an independent transaction.

1. Validate route/body shape, including UUID `commandId`.
2. Start `READ COMMITTED` transaction and set the bounded interactive lock timeout.
3. Derive firm/user from authenticated context; load Engagement and client scope.
4. Acquire the namespace locks and relational row locks in the global order fixed in ticket 003.
5. Re-authorize the exact current command.
6. Recognize a safe prior outcome or compare expected state and fail atomically when stale.
7. Recompute domain predicates and apply the domain mutation.
8. Run prepared synchronous Work reconciliation for every directly affected root.
9. Write correlated `audit_events` and required outbox intents; collect Work effects.
10. Commit. Do not call providers, email, Slack, SSE, or another service while locks are held.
11. After commit, build the requested queue delta. Projection failure returns refetch hints, not command failure.

Interactive commands use a configurable two-second lock timeout initially. A timeout returns `COMMAND_BUSY`, `retryable: true`, and a jittered `retryAfterMs`. The SPA may automatically retry the unchanged command with the same `commandId` at most twice when no user input changed. A real stale-state conflict is never automatically replayed.

Background reconcilers use the same locks and may defer/retry through outbox. A detected PostgreSQL serialization/deadlock failure may be retried once by the server with the same command identity because no external effect occurred before commit; continued contention returns a retryable conflict.

All routes below are domain-specific and validate the path target against the Engagement/client.

### Categorization and journals

```http

POST .../categorization-candidates/{candidateId}/accept
POST .../categorization-candidates/{candidateId}/reject

```

The candidate-accept command posts the candidate's accounting treatment; it does not “complete review work.” Rejecting a candidate closes that candidate and synchronously rematerializes uncategorized-transaction Work when the transaction remains unposted.

### Findings and Final Checks

```http
POST .../accounting-findings/{findingId}/resolve
POST .../close-confirmations/{confirmationId}/respond
POST .../close-confirmations/bulk-respond
```

Finding correction may delegate to a journal/accounting primitive inside the same transaction. It cannot insert an acknowledgement and separately attempt the correction after commit.

For `transaction_dated_in_closed_period`, registered Finding strategies are constrained to:

- a safe non-mutating match to an existing accounting entry;
- categorization/matching with a validated open `fs_date` while preserving bank date; or
- direct cascading reopen when the actor already has authority.

Requesting another actor's reopen decision is not a Finding Resolution and uses the Period Reopen Request routes below. A safe match command must prove it changes no closed-period ledger fact.

### Monthly close and Packages


Creating a Reopen Request requires the initiating Finding where applicable, requested starting Fiscal Period, nonblank reason, and current impact hash. It creates/reroutes Client Lead Work but leaves every covered retroactive Finding unresolved. Approval and rejection both require the exact `expected.requestVersion` and `expected.impactHash` the reviewer saw. Approval runs the complete cascade in the same transaction. Rejection requires a nonblank note, resolves only review Work, and returns every still-open covered Finding Work to its current eligible bookkeeper. ## 10. Explicit bulk manifests

The launch scope does not execute an unbounded, moving “all currently matching” query from a command body. That would make retries capable of capturing targets that were not present when the user clicked.

The workspace read returns a bounded explicit manifest for each safe bulk action:

```ts
type BulkActionManifestDto<TExpected> = {
  commandCode: string;
  label: string;
  groupKey: string;
  groupVersion: string;
  eligibleCount: number;
  limit: number;
  truncated: boolean;
  units: Array<{
    targetType: string;
    targetId: string;
    workItemId: string;
    expected: TExpected;
  }>;
};
```

Maximum independent units per request is 100. If 240 candidates are eligible, the UI says `Post next 100 safe suggestions`, not `Post all`, and the next confirmed projection supplies the following manifest. Confidence thresholds and safe eligibility are computed by the registry/adapter; the browser cannot widen them with a query parameter.

The user still performs one click. The explicit manifest is already in the workspace payload, so there is no extra round trip merely to freeze the selected targets.

## 11. Independent bulk request and response

```ts
type IndependentBulkCommandBody<TInput, TExpected> = {
  commandId: string;
  input: {
    groupKey: string;
    groupVersion: string;
    units: Array<{
      targetId: string;
      workItemId: string;
      input: TInput;
      expected: TExpected;
    }>;
  };
  presentationContext?: QueuePresentationContextDto;
};

type BulkCommandResultDto<TUnitResult> = {
  outcome: "complete" | "partial" | "none_applied";
  requestedCount: number;
  appliedCount: number;
  alreadyAppliedCount: number;
  failedCount: number;
  units: Array<{
    targetId: string;
    status:
      | "applied"
      | "already_applied"
      | "stale"
      | "invalid"
      | "forbidden"
      | "failed_transient";
    retryable: boolean;
    result?: TUnitResult;
    error?: Pick<CommandErrorDto["error"], "code" | "message" | "conflict">;
    workEffects: WorkEffectDto[];
  }>;
};
```

Rules:

- Validate envelope shape, manifest size, duplicate targets, and Engagement scope before scheduling units.
- Execute units with bounded server concurrency, initially eight or less when the database pool requires it.
- Each unit takes its own locks, reauthorizes, validates its expected state, commits domain truth and Work atomically, and returns independently.
- Preserve request order in the response even though execution is concurrent.
- Carry the parent `commandId` through every unit result/effect and identify each unit by its explicit target ID; unit correctness comes from that target's expected/domain state, not a derived retry key.
- Return HTTP `200` when the bulk request itself executed, including partial or zero applied outcomes. Do not use `207`; the discriminated unit statuses are the contract.
- A malformed/oversized envelope fails before any unit starts. Runtime unit failures do not roll back unrelated successes.
- Retrying the same manifest converges: successful units become `already_applied`, still-invalid units remain visible, and no new targets are added.

Categorization-candidate acceptance, generated/close-relevant journal post/void, and permitted multi-month Confirmation responses use this contract.

## 12. Aggregate bulk is different

`submitClosePackage`, `approveClosePackage`, `reviewAndClosePackage`, and `cascadeReopen` are not independent bulk endpoints. The user chose one bounded aggregate outcome whose partial application would violate chronological or approval invariants.

They therefore:

- use one transaction;
- lock every affected period chronologically;
- prevalidate every month before the first mutation;
- either commit every monthly transition or none;
- return one command outcome plus all Work/queue effects;
- require the Package to be split before a clean prefix proceeds separately.

This distinction is semantic, not an API option such as `allOrNothing: true`. The route fixes the transaction mode.

## 13. Queue delta contract

When `presentationContext` is supplied and still authorized, the post-commit query service returns:

```ts
type QueueDeltaDto = {
  contextKey: string; // canonical hash of effective authorized context
  generatedAt: string;
  header: QueueSnapshotDto["header"];
  clientFacetChanges: Array<{
    clientCompanyId: string;
    change: "upsert" | "remove";
    facet: ClientFacetDto | null;
  }>;
  groupChanges: Array<{
    groupKey: string;
    change: "upsert" | "remove" | "outside_window";
    sectionKey: QueueSectionKey | null;
    sortKey: string | null;
    row: WorkGroupRowDto | null;
  }>;
  close: {
    change: "replace" | "unchanged";
    cluster: CloseClusterDto | null;
  };
};

type QueryInvalidationDto =
  | { query: "queue_snapshot"; contextKey: string | null }
  | { query: "work_group"; groupKey: string }
  | { query: "close_workspace"; engagementId: string }
  | { query: "close_review"; periodCloseVersionId: string }
  | { query: "period_reopen_request"; periodReopenRequestId: string }
  | {
      query: "client_domain";
      clientCompanyId: string;
      resources: Array<
        | "bank_transactions"
        | "categorization_candidates"
        | "journals"
        | "ledger"
        | "fiscal_periods"
      >;
    };
```

The cache adapter is generic:

1. apply only when `contextKey` matches the cached queue;
2. remove each changed group from every existing section;
3. insert an `upsert` row into its server-specified section by opaque `sortKey` and truncate to the cached section limit;
4. treat `remove`/`outside_window` as absent from the current page;
5. replace the header, affected client facets, and close cluster;
6. silently execute the invalidation hints afterward.

The SPA does not derive priority, actionability, section placement, close readiness, or authorization from Work effects. If no presentation context exists or delta generation fails, it invalidates the named queries and keeps safe explanatory state until refetch completes.

The read DTO from ticket 005 must therefore include the canonical `contextKey` on `QueueSnapshotDto` and opaque `sortKey` on Work Group and Close Client rows. These are projection mechanics, not stored fields or security tokens.

## 14. Server-confirmed interaction behaviour

- Disable only the submitted control/target while a request is in flight; the row remains visible with `Saving…`, `Posting…`, or `Submitting…`.
- Do not decrement counts, move a row, mark a check complete, or advance close before a committed success response.
- On success, apply the domain result and queue delta, then move resolved targets into the in-memory handled-this-session drawer.
- In independent bulk, successful rows move out after the bulk response; failed rows remain with specific messages and retry controls.
- On `STALE_STATE`, preserve unsent user input, apply/refetch the supplied current state, and say what changed. Do not silently overwrite or automatically replay.
- If another actor or automation already resolved the target, show `Handled elsewhere` or the available actor/system label before moving it to handled state.
- On `COMMAND_BUSY` or a transport timeout, retry the unchanged command with the same `commandId` according to the bounded policy; do not present a second confirmation dialog.
- Closing the tab does not cancel an in-flight server transaction.
- A `202 accepted` response never removes the underlying Work; the UI explains what is now waiting on the provider/system.
- Do not implement the prototype's generic client-side `Undo` as a rollback of committed accounting state. Where a business action is genuinely reversible, `Undo` invokes a new authorized domain reversal command with a new `commandId` and current expected state, preserving the original audit trail and reconciling new Work from the resulting facts.

This is not optimistic accounting. The only speculative UI state is an in-flight affordance that communicates the command has been sent.

## 15. Launch refresh and realtime policy

The queue has two update paths:

1. A command issued by this browser returns a confirmed queue delta after commit. The SPA applies that delta and invalidates only the named queries.
2. A change committed elsewhere writes a coalescible `work_queue_projection_invalidated` intent to the transactional outbox. The relay publishes the invalidation through the existing Redis infrastructure, and one SSE connection for the active firm tells the SPA what must be refetched.

Client actions, teammate commands, bank processing, assignment changes, approval, and automation are normal sources of external queue changes, so SSE is part of the launch experience rather than a speculative optimization. It is still not a correctness boundary: PostgreSQL, command results, and projection DTOs remain authoritative.

Normal connected operation performs no interval polling. The SPA also follows these recovery rules:

| Condition                                              | Refresh behaviour                                                                                                                                              |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Local command committed                                | Apply its confirmed delta, then invalidate the exact named queries.                                                                                            |
| Authorized SSE invalidation                            | Refetch the named snapshot, group, close, Version, or workspace query.                                                                                         |
| Window regains focus                                   | Refetch the queue snapshot if it has not been validated since the last focus/stream event.                                                                     |
| Network or SSE reconnect                               | Resume from `Last-Event-ID`; perform a full authorized snapshot refetch before trusting the resumed stream.                                                    |
| Replay gap, unknown event schema, or permission change | Treat as `queue.reset` and perform a full authorized snapshot refetch.                                                                                         |
| Hidden tab                                             | Keep browser-managed SSE behaviour; do not start interval polling. Validate on return.                                                                         |
| SSE unavailable                                        | Start degraded visible-tab polling: queue every 30 seconds and active group/close head every 15 seconds, with ±20% jitter; stop immediately when SSE recovers. |

Fallback polling uses ETags/row versions and pauses for hidden tabs and in-flight commands. Its intervals are observable system configuration, not firm-facing settings. It is a resilience path for a broken/unavailable stream, not the normal synchronization model.

## 16. SSE invalidation contract

Endpoint:

```http
GET /api/v2/firms/{firmCompanyId}/work-queue/events
Accept: text/event-stream
Last-Event-ID: optional
```

Event:

```text
id: opaque-retained-stream-id
event: queue.invalidated
data: {
  "schemaVersion": 1,
  "committedAt": "...",
  "projectionRevision": "...",
  "context": "firm",
  "engagementIds": ["..."],
  "groupKeys": ["..."],
  "closeChanged": true,
  "originCommandId": "..."
}
```

Rules:

- send invalidations, never full accounting records or queue DTOs;
- open exactly one stream for the stable active firm, not one per client, group, or workspace;
- authenticate and authorize the connection to that firm, then filter every Engagement/group reference to the viewer's current effective scope before sending it; if nothing authorized remains, send nothing;
- re-evaluate or reset the stream when firm membership, Engagement responsibility, or oversight capability changes;
- deliver at least once, preserve a monotonic retained stream ID/revision, and coalesce repeated invalidations without losing the broadest affected projection;
- let a browser ignore its own correlated echo only when its confirmed command delta declares that it completely covers the same projection revision; otherwise refetch safely;
- have the client refetch only named groups/close/workspaces plus the snapshot when section counts, facets, or ordering may have changed;
- on retention gap, permission change, or unknown event version, emit/handle `queue.reset` and perform a full snapshot refetch;
- write invalidation intent in the same transaction as the source/Work change, then publish after commit into a retained Redis Stream; Redis is delivery infrastructure, never accounting or Work truth;
- reconnect/refetch from PostgreSQL after Redis or SSE failure, so lost delivery can delay visibility but cannot lose or corrupt Work;
- use degraded polling only while the stream is unavailable;
- no WebSocket is needed for one-way invalidation.

## 17. Accountable Books integration findings

Reusable foundations:

- request context already distinguishes per-attempt request identity from correlation identity; V2 maps public `commandId` into the existing internal correlation field;
- `audit_events` already stores request/correlation identity;
- candidate lifecycle and ledger source linking already contain useful idempotent/race-aware patterns;
- the advisory-lock utility and source mutation services provide the right serialization primitives;
- outbox already commits with domain state, coalesces by intent/scope, and retries safely;
- TanStack Query already supports targeted invalidation in the SPA;
- existing controllers already use `409` for changed facts in some close/banking paths.

Required Work Queue and Close V2 integration corrections:

- add required body `commandId` handling for Work Queue and Close V2 commands and propagate it through existing correlation infrastructure without treating it as deduplication;
- introduce the structured Work Queue and Close V2 error/conflict envelope rather than returning free-form `error` objects;
- ensure queue-affecting user commands call Work Queue and Close V2 Work synchronization inline instead of relying on the legacy asynchronous Work materializer;
- add the coalescible queue-invalidation outbox intent, Redis Stream relay, and authorized firm-scoped SSE endpoint;
- return domain results, Work effects, and projection invalidations from one command wrapper;
- do not copy the existing frontend pattern of broad query invalidation after every mutation when exact targets are known;
- preserve the new banking distinction: failed active sync runs retry internally, `requires_action` creates client Work, and `revoked` produces disconnection notification only.

## 18. Acceptance scenarios

1. A transaction categorization and its Work resolution commit together; the queue row remains until the response arrives.
2. The response is lost after commit; retrying the unchanged command with the same `commandId` returns `already_applied` and current deltas without another ledger posting.
3. A defective client reuses a `commandId` with a different account selection; no key-reuse protocol runs, but authorization, expected state, locks, and ledger uniqueness still govern the command and prevent the ID from bypassing correctness.
4. Another user posts the transaction first; the old command returns `target_resolved`/current outcome and never double-posts.
5. A 50-candidate bulk has 46 valid, two stale, one forbidden, and one transient failure; 46 commit independently and four remain visible with exact reasons.
6. Retrying that manifest does not include a newly arrived candidate and does not repost the 46 successes.
7. An unsafe uncategorized transaction never appears in a candidate bulk manifest.
8. Package approval finds one stale Version; no month in the Package closes.
9. An accounting change during pending approval stales the Version, resolves approval Work, and makes the Lead's old approval request return `approval_stale`.
10. A Confirmation answer from an old context is rejected; a same-context exact retry creates no second effective response.
11. A command commits but delta rendering fails; the client receives success plus refetch hints and does not retry as though accounting failed.
12. A lock timeout produces a bounded same-`commandId` retry; a semantic stale conflict is shown to the user and never auto-replayed.
13. Bank reauthorization session creation returns accepted, uses integration-local idempotency where the provider requires it, and keeps Work visible until verified connection state changes.
14. A Client Lead approves while the Primary Bookkeeper watches; the committed invalidation reaches the same firm stream, the bookkeeper refetches the named close projection, and no client context switch occurs.
15. An SSE/Redis interruption cannot lose truth: the browser enters degraded polling, reconnect/refetch from PostgreSQL recovers, and the event contains no unauthorized accounting detail.
16. Accepting a historical Package with a future deadline atomically replaces routine deadlines on all covered open Close/Work rows; retry converges without duplicate changes.
17. A reasoned Package deadline change updates the Package and every covered open Close/Work row or none; a stale `packageVersion` changes nothing.
18. Splitting a Package requires explicit deadlines for all replacements, while reassignment preserves the existing deadline exactly.
